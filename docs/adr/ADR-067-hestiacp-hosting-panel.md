# ADR-067: HestiaCP is the hosting panel (replaces the CloudPanel node-agent design, ADR-020)

- Status: **Proposed** (owner request 2026-11-24; binding once the owner accepts it)
- Supersedes: ADR-020 (CloudPanel automation path). D-20 is answered by this record.
- Evidence: HestiaCP CLI reference https://hestiacp.com/docs/reference/cli and REST API page https://hestiacp.com/docs/server-administration/rest-api (read 2026-11-24); the output of Hestia's own `v-list-*` scripts in https://github.com/hestiacp/hestiacp (`bin/`), and the API examples https://github.com/hestiacp/hestiacp-api-examples.

## Context
Shared hosting ran on a design built around CloudPanel: its CLI has no remote surface, no site listing, no cron/logs/SSH/FTP/PHP-settings commands, a licence question (ADR-020, HG-06-01) and a history of privilege escalations, so ADR-020 proposed a bespoke signed-envelope node agent. That agent was never built beyond a simulation.

## Decision
1. **HestiaCP is the only hosting panel.** Each node runs HestiaCP; the platform reaches it through Hestia's **REST API** (`POST https://<panel fqdn>:<port>/api/`, `hash=ACCESS_KEY_ID:SECRET`, `cmd`, `arg1..N`, `returncode`), with a per-node access key restricted to an allow-listed command profile. No node agent, no shell strings, no browser-supplied host, command or key.
2. The **site is a Hestia account** whose name is the token-derived `s-<hex>` of the hosting contract: `findByToken` is `v-list-user`, so reconcile-before-retry needs nothing else (a lost answer on a mutating command is `uncertain`).
3. The panel connection (FQDN, port, optional pinned TLS fingerprint, vault reference of the access key) lives on `hosting.nodes`; the key is typed once in the admin console (write-only, sealed; production waits on D-12) or supplied as a vault reference.
4. Limits are Hestia **packages** assigned by the platform; the node setup creates them. No CPU/RAM guarantee is claimed until a measurement and enforcement mechanism is proven on a real node.
5. Not in this decision (later sprints, each its own session): VPS with an auto-installed Hestia (Alibaba SCCC Riyadh, Contabo EU), SFTP file manager, cron/logs/FTP/HTTP-auth/PHP tools, business email, per-site isolation tests on a real node. WordPress, off-server backups, restore drills, monitoring, packages and the node setup script are [ADR-068](ADR-068-hestia-backups-wordpress-monitoring.md).
6. The previous simulation is kept only as test doubles under `hosting/internal/mock/sim/` (platform logic tests: capacity, reconcile, quotas, abuse); it is not a product path.

## Consequences
- Everything is NOT VERIFIED until a human-run probe against a real node (the owner supplies the node and the key). The REST page documents the return codes and the access-key mechanism but not the request format; the format used here is that of the official examples repository (`POST /api/`, form fields) and must be confirmed by the live probe.
- Hestia's `v-list-web-domain-ssl` returns the private key with the certificate: the adapter parses the expiry only and drops the rest.
- Backups, custom certificates, databases (M08), Node.js/Python runtimes and reverse proxies are `unsupported` in the adapter until built and tested.
- CloudPanel data (the old node-agent tables) stays in the database (forward-only migrations) but nothing writes to it. Existing sites in this repository's dev databases are demo data on a simulation; no real CloudPanel node ever existed.

## Addendum S04 (2026-11-24): a VPS that installs HestiaCP
- **Product.** The purchase page offers a control-panel choice (`spec.panel`: none, or HestiaCP with an explicit template and an explicit mail yes/no). It is stored in the order snapshot (image, template, region, provider plan, Hestia version, installer URL and digest) in `commerce.quotes.preferences` and copied to `compute.panel_installs` (one row per order and per instance: a unique constraint, not application code, prevents a second server). Only placements listed in `HESTIA_VPS_CONFIG` are sold (default: Alibaba ECS via SCCC Riyadh `me-central-1`, Contabo `EU`); there is no fallback between regions. Only images an administrator verified for the configured version are offered, and only where the provider states cloud-init (Alibaba `IsSupportCloudinit`; Contabo standard images) and Hestia documents the OS (Debian 12/13, Ubuntu 22.04/24.04/26.04). Feature flag `cloud.hestia_vps`, default off.
- **Bootstrap.** cloud-init user data (Alibaba `UserData`, Base64, documented ≤ 32 KB; Contabo `userData`) is a pure function of the order, so a retry is byte-identical (Alibaba rejects a replayed `ClientToken` with changed parameters). The script downloads the PER-OS installer, checks its pinned SHA-256 BEFORE running it, installs non-interactively with the documented flags, creates a READ-ONLY access key (custom command profile, only `v-list-sys-info`, `v-list-sys-php`, `v-list-web-templates-backend`) and registers once. The admin password of the panel is generated on the server and never sent.
- **Registration.** `Authorization: Bearer nzr1.<registration id>.<256 random bits>`: only its SHA-256 is stored; the secret is sealed in the vault, read back to build identical user data and deleted when consumed. Bound to one order and one server; its window starts when the provider created the server; consumed atomically (concurrent registrations: exactly one wins). The caller's address must be one of the server's public addresses as the PROVIDER reports them, and the provider's record must show that server running in the sold region (with our instance tag where the provider has tags). A mismatch is refused without consuming the secret.
- **Stages.** create server → wait for boot → install panel → register link → readiness test → ready, or needs attention / held. Every transition is a compare-and-set on the stage; duplicates and restarts cannot skip or repeat one. Resume never creates, replaces or wipes a server: Nuzm-side problems continue from their stage; a bootstrap that did not finish on the server extends the window of the SAME order and server and asks the root user to re-run the script that is still on it; a failed integrity check is not retried on that server. A provider-side reinstall (which would erase customer data) is not offered: no adapter implements it, so no data-erasing step exists to confirm.
- **Capacity.** A capacity refusal at the provider holds the order (`held`, reason `provider_capacity_unavailable`) in its sold region, the cost authorization stays, and the same operation is retried later in the same region; the customer can cancel it (released, no charge).
- **Network class.** The registered node is `network_class = customer_vps`, owned by the organization, never `active` (a check constraint), and every placement/capacity/plan query reads `shared` nodes only. Provider start/stop/restart go through the provider API and do not depend on the panel link; the link state (`connected`/`lost`) is tested periodically and shown separately.
- **NOT VERIFIED.** Everything above ran against the mock provider, the Alibaba/Contabo simulators and a fake node registry. The `v-add-access-key` JSON field names and the `API_ALLOWED_IP` setting name come from Hestia's own sources, not from the cited documentation pages; the script reports `key_failed` rather than guessing, and the first live install must confirm both.
