# ADR-068: Backups, Managed WordPress and monitoring on HestiaCP

- Status: **Proposed** (HestiaCP sprint S06 and the WordPress part of S03, 2026-11-24; binding once the owner accepts it)
- Builds on: ADR-067 (HestiaCP is the hosting panel). Touches D-07 / P-M06-1 (the production backup store), which stays OPEN.
- Evidence: HestiaCP CLI reference https://hestiacp.com/docs/reference/cli, backup and restore guide https://hestiacp.com/docs/server-administration/backup-restore, packages https://hestiacp.com/docs/user-guide/packages.html, REST API https://hestiacp.com/docs/server-administration/rest-api (v1.10.9 pages, read 2026-11-24), and the official repository's `web/src/app/WebApp/Installers/WordPress/WordPressSetup.php` + `web/src/app/System/HestiaApp.php` for how Quick Install runs. Nothing below has run against a real node: every claim about Hestia's behaviour is either quoted from those pages or marked NOT VERIFIED.

## Decisions

### 1. Backups are off the node, measured by the control plane, not by Hestia
1. Hestia writes the archive and uploads it to the node's remote backup host (set at node setup with `v-add-backup-host`, which is NOT in the REST allow-list because it carries the host's password). The platform schedules (`v-schedule-user-backup USER`), then waits for the archive to appear in the **off-server store of the node's data region** and measures it there (size, streamed sha256). The store, not Hestia's return, is the proof: Hestia documents no return codes for the backup commands.
2. The existing `BackupSink` contract gains optional `list`, `stat`, `refOf` and `health` (an adapter whose archives the node uploads itself needs them); `BackupRef` gains `archiveName`, `encrypted` and a `snapshot` (domains, database count); `HostingAdapter` gains optional `listBackups` and `deleteBackup`; `site_backups` gains `archive_name` and `provider_state`. The service flow, the API and the tables of M06 are otherwise unchanged. A reference is `<region>/<site account>/<archive>`; the production implementation is `RegionDirectorySink` (a directory per region = the region's backup host storage, every path segment validated).
3. **Idempotency across retries and restarts.** Before the first schedule the service persists the set of archives that already existed and, before sending the schedule, that it is being sent (`provider_state.known/scheduledAt`). A retry or a restarted worker only WAITS for the new archive; a lost answer to the schedule can therefore never produce a second archive. An archive counts only after its size is identical on two looks (an SFTP target shows a file while it is still being written).
4. **Encryption.** Hestia documents none for its archives. The row and the API say `encrypted: false` instead of claiming the per-site key of the old contract; the region's store is the protection (disk encryption, access limited to the backup account and the worker) and is a go-live check. Hestia stores SFTP/FTP backup passwords in plain text (its own warning): the backup account may write only its node's directory.
5. **Schedule and retention.** The platform runs ONE schedule: one `scheduled` backup per active site per day for plans with a backup quota; a site at its backup-count limit expires its oldest SCHEDULED backup first (a quota filled by the customer's own backups is never touched; the monitor raises `backup_missing`). Hestia's own nightly `v-backup-users` job is removed at node setup so there is one schedule with a row, a checksum, a quota and a residency check for every archive. Retention deletes the store copy and, best effort, the node copy (`v-delete-user-backup`). Residency: the site's data region must be allowed for the organization (existing hook) and the store is chosen by the node's region.
6. **Restore** uses `v-restore-user` (synchronous; `v-schedule-user-restore` is not used because its completion cannot be observed). Before anything is touched the archive's checksum is compared with the recorded one (a tampered archive is refused and marked corrupt). `v-restore-user` needs the archive in the node's `/backup`: if it is not there an `ArchiveStager` copies it; whether Hestia fetches it from the remote host itself is NOT DOCUMENTED, so on a real node restore is reported `unsupported` until the stager exists or a live check proves it unnecessary. After the restore the account is compared with the snapshot taken at backup time (domains present, database count not lower). A lost answer is settled by that comparison, not by a retry.
7. **Restore drills** prove the above on a real backup: a node with `purpose = restore_drill` (a database CHECK keeps it out of `active`; the capacity allocator already takes only active nodes), in the backup's own data region (else 403 residency_denied), receives the restore; the account, the snapshot and (WordPress) the site's admin page are checked; the account is then wiped and a wipe that leaves anything fails the drill. The duration and the per-check result are the record (`hosting.restore_drills`).

### 2. Managed WordPress is reproduced from Hestia's documented commands
1. Hestia's Quick Install is panel PHP: no CLI command and no REST entry exist for it. `WordPressSetup.php` calls `v-delete-fs-file` (placeholders), `v-add-user-wp-cli`, `v-add-database`, then WP-CLI through `v-run-cli-cmd <user> /usr/bin/php<ver> <home>/.wp-cli/wp …` (`core download`, `config create`), installs by an HTTP POST to `wp-admin/install.php?step=2` (a WP-CLI quirk with spaces in the title), and sets the `wordpress` web template. The platform runs the same commands over the REST API with the same allow-list discipline, as the site's own non-root user. Differences: the install is `wp core install` (the title is the site's domain: no space, customers rename the site in WordPress) and every WP-CLI argument must be one token of `[A-Za-z0-9_.:/@=+,%-]` (nothing with a space, quote, `$`, `;`, `|`, `&`, backtick), the PHP binary must be `/usr/bin/php<x.y>` and the WP-CLI path that of the same account.
2. **The install is driven by what the site SHOWS, not by what the platform remembers**: an HTTP look against the node (Host header = the site's name) classifies the site as `none` / `unconfigured` (redirect to `setup-config.php`) / `uninstalled` (redirect to `install.php`) / `installed` (`wp-login.php` served). Each phase runs only its own step, and WP-CLI itself refuses to download over, configure or install over an existing site, so a retry, a restart or a second worker resumes at the right step and cannot destroy content. A step whose answer was lost is settled by looking again. `ready` is declared only when the site answers, no installer redirect remains and `wp-login.php` is served.
3. **Secrets.** The admin and database passwords are generated server-side (32 characters of `[A-Za-z0-9]`), held in the vault by reference, never in a table, response, log or audit entry. The admin access reaches the customer ONCE: `POST …/wordpress/handover` returns it and consumes it with a single conditional update (two parallel calls cannot both get it), deletes it from the vault and answers `Cache-Control: no-store`; it deliberately takes no Idempotency-Key (a replay store would keep the password); unread it expires after 7 days; a reset (`wp user update`) issues a new one. The passwords are WP-CLI arguments for a few seconds on the node: the setup script mounts `/proc` with `hidepid=2`.
4. A plan carries `app_kind` (`wordpress`); the site copies it; when the site becomes `active` the install operation is queued (idempotent: one `site_apps` row per site; a sweep re-queues a missing row or a pending row without a live operation). The site is `active` before WordPress is `ready`: payment, site activation and application state are separate states.
5. Limits: the install uses the platform's placeholder domain; binding a customer domain later does not rewrite WordPress's own URL (not built). The admin email is a non-delivering address on the site's domain (`wp-admin@<domain>`): the customer sets a real one in WordPress.

### 3. Packages, access profile and monitoring
1. One Hestia package per plan, `nz-<plan key>`, rendered from the plan (`renderPackage`, the keys of Hestia's shipped `default.pkg`; `SHELL='nologin'`; DNS 0; no CPU/RAM value) and served by `GET /v1/admin/hosting/node-packages`; the node setup script creates them. The REST access-key profile is generated from the adapter's allow-list and a test fails on drift. **Risk R-1:** a key that may run `v-run-cli-cmd` can run a command as a site user; one key per node, a tight API address allow-list, and a second key for the WordPress role are the mitigations (a second key needs a second panel-key reference on the node: not built, proposed).
2. Monitoring is a sweep that COMPUTES the conditions that hold now and opens one alert per (kind, scope) (a partial unique index makes opening idempotent), refreshes it while it holds and resolves it when it is gone; a probe that fails resolves nothing. Kinds: capacity, activation failed/stuck, WordPress failed, certificate failed/expiring, backup failed/missing, backup store unreachable, panel link (a live health call that also checks Hestia's web, database and PHP-FPM services), restore drill failed. Health of the panel now includes `v-list-sys-services`.

## Consequences
- All of it is NOT VERIFIED against a real node; the live checks are in docs/runbooks/node-onboarding.md. D-07 (production store, encryption at rest) and the restore staging path stay open.
- `VaultPort` gains `read` (the handover and the install read secrets they created); there is still no production vault (D-12).
- Migration 1981 (forward-only): `nodes.purpose`, `plan_definitions.app_kind`, `sites.app_kind`, `site_backups.archive_name/provider_state`, tables `site_apps`, `restore_drills`, `monitor_alerts`.
