# CONTRACT-3 — PROPOSAL (not requested for this batch): `ModelAdapter` contract 1.2 for token classes

- **Requester:** Session 02 · **Contract:** `packages/adapters/model/src/types.ts` (mine) + `ai.model_usage` columns (needs a migration and classification rows) + `ProviderPricing` · **Additive:** yes · **Status:** design note, nothing implemented
- **Gap G11:** `Usage` is `{inputTokens, outputTokens}`. The Claude Messages API reports `cache_creation_input_tokens` and `cache_read_input_tokens` separately and prices them differently from plain input. The adapter never asks for caching (no `cache_control` is sent), so these counts are zero/absent today and billing is correct; they would matter the moment prompt caching or provider-side reasoning/thinking tokens are used (the adapter currently leaves thinking at the model default and bills only the reported output tokens).
- **Proposed text:** `Usage` gains optional `cacheCreationInputTokens?`, `cacheReadInputTokens?`, `reasoningTokens?` (all non-negative integers, default 0); `ProviderPricing` gains optional per-class multipliers; `ai.model_usage` gains the same three bigint columns (expand-only, default 0) so a report can split them. A rate card entry could carry `creditsPerMillionCachedInput`. Until the owner decides prices for these classes (D6) the gateway must keep charging them as input tokens (the conservative, platform-favouring choice) and record the split for reporting only.
- **Decision needed from the owner (D6 extension):** whether caching/reasoning tokens are priced separately for customers. **Do not implement before that decision.**

**Master answer:** design note only, NOT applied (D6 extension is owner-blocked), per the Master's message of 2026-11-24.
