# CONTRACT-S05-P2-1 — the builder agent loop as a mode of the `webapp` run kind

- Requester: Session 05 (Phase 2) · Contract: `spec/openapi/openapi.yaml` (description text only) · Status: ACCEPTED and applied by the Master 2026-11-24 · Additive: yes, no schema, enum or route changes.
- What exists: the lifecycle (18 steps: requirements → project analysis → architecture/template → plan → tasks → file generation → validated change apply → review → execution request → build → error analysis → repair → apply repair → rebuild → tests → preview → deployment preparation → deployment approval request) runs as a **mode of the existing `webapp` run kind**: `POST /v1/ai/runs` with `kind: webapp`, `input: { builderLifecycle: true, brief: { prompt }, maxRepairRounds?: 1..3, maxMinutes?: 1..60 }`. Same pattern as S-AG3's `input.agentic`.
- Why a mode, not a new kind: `ai.runs.kind` has a database CHECK (`website|edit|chat|webapp|mobile|test-fix`) and the OpenAPI `Run.kind` enum. A new kind would need a migration and an enum change; a mode needs neither, keeps the existing approvals inbox, cancellation and segment engine, and leaves the run-kind registry alone.
- **Master-owned registration lines: NONE were needed.** I did not touch `apps/api/src/modules/ai/**` (the single `ALL_KINDS` line stays as it is). The handler registration is `WebappRunHandler` in `apps/api/src/modules/appbuilder/**` (my own path): it received one constructor argument, `BuilderLifecycleService`, injected in `appbuilder.module.ts`.

## Proposed text (append to the description of `POST /v1/ai/runs`)
`A webapp run with input {builderLifecycle: true, brief: {prompt: 1..4000 characters}, maxRepairRounds?: 1..3, maxMinutes?: 1..60} runs the builder agent loop: it analyses the brief, plans, writes the plan's files as ONE validated change (AI branch only), reviews, builds and tests through the Execution Gateway, repairs failures within hard limits (3 repair rounds, 2 attempts per step on a transient error, 60 steps, the run's token and credit budget) and ends by asking for a deployment approval (approval type production_deploy, decided by an owner or admin in the approvals inbox). It deploys nothing. Served only while the organization flags builder_tools.enabled and builder_lifecycle.enabled are on (otherwise the run ends unsupported_capability). Build and test results are SIMULATED (a mock execution port) until the sandbox runtime is approved (D-21, HG-10-02, ADR-067); the result says so (simulated: true). 422 validation_failed for a malformed input; the usual 402/403/422/429/503 of run creation.`

## Observable behaviour (all covered by `builder-lifecycle.int.spec.ts` on the real run engine, and by `lifecycle.runner.spec.ts` / `machine.spec.ts` without a database)
- Events on `GET /v1/ai/runs/{id}/events`: `lifecycle_started`, `lifecycle_step` `{step, status: started|succeeded|failed|retry|waiting_approval|denied, round, attempt?, summary?, passed?, code?, approvalId?, progress}`, `lifecycle_finished` `{status, code, progress}`. `progress` = `{status, percent, done, total, current, repairRound, tokens, credits}`.
- One `ai.run_steps` row per step (`node` = `lc-<step>-r<round>`, agent `agent`), tokens in and out per step; the run checkpoint holds the state machine and small results, never file contents (change sets go to `ai.artifacts`).
- Audit: `builder.lifecycle.started`, `builder.lifecycle.step_finished` (every step, success or failure), `builder.lifecycle.deployment_decided`, `builder.lifecycle.finished`, `builder.execution.start_decided`, `builder.execution.simulated`.
- Result (`ai.runs.result`): `{outcome: "lifecycle", status, progress, repairRounds, versionId, deployment: {target, readiness, blockers}, simulated, note}`.
- Limits (domain `LIFECYCLE_LIMITS`; a run's own values can only LOWER them): 2 attempts per step, 3 repair rounds, 60 step runs, 120 generated files, 400 000 tokens, 60 minutes, 12 execution requests. A ceiling ends the run with `tokens_exceeded | credits_exceeded | time_exceeded | steps_exceeded | execution_requests_exceeded` (the first two map to run state `budget_exceeded`).
- Cancellation: the standard `POST /v1/ai/runs/{id}/cancellation`; honoured before every step and between generation tasks, and while parked at the approval.

## New flags (all default OFF; `platform.feature_flags`, an organization row beats the global row)
`builder_lifecycle.enabled` (the lifecycle), `builder_lifecycle.model_generation` (let a model write files and repairs through the metered gateway; off = deterministic placeholders and rule-based repairs, zero tokens), `builder.billing_separation` (see CONTRACT-S05-P2-3). `builder_tools.enabled` is also required.
