## Implementation prompt
You own the mobile build engine: from a generated Flutter project to an **installable Android APK** (T3) and a **validated iOS build on macOS with Xcode** (T4). Environment facts (checked 2026-11-24 on the owner's Mac): macOS 13.7.8, Flutter 3.35.7, Java and the Android SDK present, **full Xcode NOT installed** (Command Line Tools only). Builds execute untrusted-ish (AI-generated) project code: they run in **disposable, isolated build environments**, never as the owner's normal user with access to secrets or personal files. You define those environments and refuse to run outside them.
Deliver: (1) hardening of the Flutter project engine: spec -> project, analysis gate (secrets, cleartext rules, permissions, plugin allowlist), pinned toolchain, deterministic files; (2) **Android build environment**: a disposable environment definition (container/VM image recipe or a dedicated user-sandbox on the Mac approved by the owner) with Flutter + Android SDK + Gradle offline mirror, no network except the registry mirror, no host secrets; the build orchestrator that runs `flutter pub get`, `flutter analyze`, `flutter test`, `flutter build apk --debug|--release` with test signing only (debug/test keystore custody per B-SIGN; **never** a production key), extracts the APK, records its SHA-256, runs `apkanalyzer`/install on an emulator if available; (3) the two Flutter local tests (`MOBILE_FLUTTER_LOCAL=1`, 15–25 min CPU, pub.dev network) made reproducible inside the build environment and run in a quiet window; (4) **iOS plan and prerequisite checker**: a script that reports exactly what is missing for T4 (Xcode full install, `xcode-select`, simulator runtimes, CocoaPods, license acceptance), a macOS build recipe (`flutter build ios --no-codesign`, `xcodebuild` analyze/build for simulator, `xcrun simctl` run + screenshot), and the policy for the macOS host (owner-provided dedicated macOS user or machine; no Apple credentials needed for T4); (5) build error parsing for Gradle/Dart/Xcode errors handed to S03's repair loop; (6) releases: build artifacts, versions, signing credential **references** only (existing signing service stays reference-only).
## Scope boundaries
In: mobile module, Flutter templates, mobile build environments, mobile UI. Out: loop (S03), generic sandbox (S02: you consume its isolation design for Android; macOS builds are your own host policy), store submission (never).
## Acceptance criteria
- M1 **T3:** from a synthetic brief the real model generates a Flutter app that analyzes, tests and builds into a **debug APK** inside the isolated Android environment; APK hash recorded; installs and launches on an emulator (or `apkanalyzer` structural check if no emulator) — evidence with logs and toolchain versions.
- M2 **T4:** the same project builds for iOS **without code signing** on a macOS host with full Xcode (`flutter build ios --no-codesign` and an `xcodebuild` simulator build; simulator launch screenshot if a runtime is installed) — evidence with Xcode and Flutter versions. If Xcode is not installed, the prerequisite checker's output is the deliverable and T4 stays `NOT VERIFIED (B-iOS)`.
- M3 Automatic repair works on mobile errors (a missing dependency, a Dart type error, a Gradle version mismatch) via S03 within limits.
- M4 The two skipped Flutter tests run green in the environment, or the precise blocker is recorded.
- M5 No production signing key, no store submission, no Apple/Google account credential in any file, log or report.
