## C. Implemented features
1. **Full-stack template family**: email/password auth (scrypt, min length 10), signed expiring sessions with **server-side revocation at logout**, sign-in rate limit, **public sign-up** (option; fixed least-privileged role, never an administrator in single-tenant; rate limited; duplicate → 409), unknown-account sign-in costs a hash verification and answers identically to a wrong password, **cross-origin refusal** on state-changing requests (the session is an `Authorization` header, never an ambient cookie, so classic CSRF has no ambient credential to ride; the Origin check is defence in depth), role model with owner/team/all scope, CRUD with validation/pagination/search/filter/sort/optimistic locking/CSV/audit (Phase 2), OpenAPI 3.1 contract generated with the app (incl. sign-up), forward-only migrations with `.down.sql`, bilingual RTL SPA (Phase 2, unchanged), environment by variable only.
2. **Multi-tenancy** (`tenancy: 'multi'`): `app_tenants`, `tenant_id` everywhere, `FORCE ROW LEVEL SECURITY` + one policy per table, per-tenant uniques, composite tenant-aware FKs, tenant taken from the verified user row (AsyncLocalStorage) never from the request, fail-closed without a tenant, sign-up creates an organisation and its administrator, users and owners cannot cross tenants.
3. **Static analysis gates** (`runStaticGates`): secrets (+ canaries), forbidden APIs (`eval`, `new Function`, `vm`, `child_process`, worker/cluster, remote import, process binding, HTML-injection sinks), dependency policy (allowlist, registry-only specs, no lifecycle scripts/overrides, lockfile: https registry host allowlist, integrity, no install scripts, no unlisted package), SQL-injection patterns (interpolation/concatenation vs `$n` + `q()` identifiers), route authentication (public routes allowlist, every route reads the user and checks a permission, no second HTTP server), **platform integrity** (engine/auth/stores/probe byte-pinned by hash; a generated app cannot weaken them or forge a probe). Findings never quote source. `repairBrief` turns blockers into repair items (rule, file, line, fixed remediation sentence) for P3-S03's loop.
4. **Run-and-probe**: platform-owned `probe/run.ts` (inside the runtime: ephemeral PostgreSQL → migrate twice → start the app as production does with a minimal explicit environment → 13 required checks over HTTP → one report line → teardown) and the platform side `probe-runner.ts` (static gates → runtime port → untrusted-output parser that recomputes every count and the verdict → evidence record whose label comes from the runtime's **origin**). Runs today only on the **simulated runtime** (`runInRuntime`, simulated mode).
5. **DB provisioning** (design `DESIGN-P3-S05-app-database.md`): in-sandbox ephemeral PostgreSQL (non-superuser role, loopback, random credentials, destroyed with the workspace) and a managed-DB service for staging (`AppDatabaseProvisioner`: vault references only, idempotent, reconcile-before-retry, residency seam, tenant-scoped, destroy-with-workspace, orphan sweep, audit) over **simulated** ports; `checkAppEnvironment` (allowlist, no platform host/secret, references only).
6. **Product generators** (`productApp`): CRM (the reference CRM with money as integer minor units), ERP (suppliers, items, stock, purchase and sales orders with lines), SaaS (multi-tenant: projects, tasks, members, plans, subscriptions; organisation sign-up), e-commerce back office (categories, products, customers, orders, lines). Each is validated by the builder's `validateAppSpec`, type-checks as a generated project, passes the gates and the workspace secret screen. **Not included, stated in each result (`notIncluded`)**: payment capture, tax/ZATCA, invoicing, shipping, a public storefront/cart.

No API route, flag, migration file or UI screen was added (see CONTRACT-P3-S05-2); the generated app's own screens are the Phase 2 SPA.
