# M10B spec change requests (SCR) — PENDING OWNER APPROVAL

The M10 prompt and docs/04 §2.10 define `POST/GET /v1/mobile/builds`, `GET /v1/mobile/builds/{id}` (+ `/artifacts`), `POST/GET /v1/mobile/signing-credentials` and `POST/GET /v1/mobile/releases`. **Exactly those are implemented.** The items below need a path docs/04 does not have; none exists in the code or in `spec/openapi/openapi.yaml` (status: BLOCKED until the owner approves a path). Where a screen or test needs the behaviour, M10B ships a service-level operation (tested) and the UI shows the control disabled with the reason.

| SCR | Proposed endpoint(s) | What is blocked meanwhile |
|---|---|---|
| **SCR-M10B-01** | `POST /v1/mobile/signing-credentials/{id}/revocation` (and `GET …/{id}`) | Revoking a signing credential reference. The column `mobile.signing_credential_refs.revoked_at/revoked_by` and the DB guard exist; `activeFor()` ignores revoked rows. No HTTP route, no UI button (UI-M10-15 shows revoke disabled). Until approved, the interim lever is the vault itself (delete/rotate the material behind the reference). |
| **SCR-M10B-02** | `GET /v1/mobile/releases/{id}` · `POST /v1/mobile/releases/{id}/owner-approval {scopeHash}` · `GET /v1/mobile/releases/{id}/submission-preparation` | The account-owner approval step (UI-M10-17), reading one record, and the "submission preparation export". Implemented as `ReleaseService.ownerApprove` (owner only, bound to `scopeHash`, stale = 409, final and immutable by DB trigger, idempotent) and `ReleaseService.submissionExport` (refuses before approval, assembles a manifest, **calls no store**). Without a route the approval cannot be performed through the API in this milestone: `owner_approved` is reachable only in tests. Permission proposal: `mobile:release:approve` (owner role only; seeded by migration 1500). **No route may submit to a store**; the platform does not do that unless the owner separately authorizes it and it is added to the spec. |
| **SCR-M10B-03** | `GET /v1/builder/projects/{id}/previews` semantics for `type=mobile` (web-rendered Flutter) | S48.4 asks for web-rendered previews through `/v1/builder/projects/{id}/previews`. M09's preview store serves the rendered site of a *website* version; Flutter web output needs a web build worker and a preview store for the build output (artifact kind not in the `mobile.artifacts` enum: `apk\|aab\|ipa\|symbols`). Previews of mobile projects answer **422 `unsupported_capability`** with the "preview is not a guarantee of device behaviour" statement. `flutter build web` is NOT claimed. |
| SCR-M10B-04 | `GET /v1/mobile/builds/{id}/artifacts/{artifactId}/download` (signed, ≤15 min URL) | Downloading an artifact. The object store is M08 (bucket per region); no download route exists, only metadata with `sha256` (an owner cannot fetch the APK through the API yet). |

## Interpretations made without a new endpoint (for the owner to confirm)
1. A mobile project is created by `POST /v1/builder/projects {type:'mobile'}` (docs/04) and lives in the M09 builder tables (`builder.projects/project_versions/project_files`); the version's model column holds a small mobile manifest, which is the only change to the M09 storage model (migration 1510 widens the `type` CHECK; the M10A web-app work needs the same widening).
2. `POST /v1/mobile/builds` returns 202 with the build record (its `id` is also the `operationId`); there is no separate `platform.operations` row (the same simplification M10A made for test runs). Builds are claimed atomically, so a second execution is a no-op.
3. `POST /v1/mobile/releases` with `status: 'prepared'` performs the checklist validation (422 `release_checklist_incomplete`); `draft` stores what is entered and returns `missing`. A **signed** succeeded build is part of the `prepared` checklist (with no signing stage, HG-10-01, nothing can reach `prepared` in a real environment: stated, not faked).
4. Error codes added (append-only block `M10B error codes`): `signing_not_authorized` (422), `signing_unavailable` (503), `no_macos_capacity` (503), `build_runner_unavailable` (503), `raw_secret_rejected` (422), `release_checklist_incomplete` (422), `owner_approval_required` (409).
5. Permissions `mobile:build`, `mobile:signing` (owner, admin), `mobile:release`, `mobile:release:approve` (owner only) are PROPOSALS seeded by migration 1500 (catalogue in M01).
6. New run kind input: `/v1/ai/runs kind=mobile` takes `{description}` only (3..600 characters); the design agent returns a structured spec, approval kind `plan` (M09's) gates writing the project; AgentTask `mobile_design` was added to M09's union and `mobile` to its served kinds.
