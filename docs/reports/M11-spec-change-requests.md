## Interpretations of docs/04 made without a new endpoint (for the owner to confirm or reject)
1. `POST /v1/agencies/{id}/clients`, `…/delegated-access` and `POST /v1/resellers/{id}/sub-organizations` serve **both sides**: the caller's organization decides (the agency/reseller proposes; a linked client/sub-org answers `{linkId|grantId, decision}`), as the docs/04-derived table says "A (and client admin approves)". Permission floor on the route is `org:read`; the handler requires `agency:manage` / `reseller:manage` (proposing side) or `partners:manage` (answering side, new permission).
2. **Inbound workflow webhook trigger** `POST /v1/webhooks/workflows/{token}` is not in §2.11; it follows the §1 convention for inbound webhooks (`/v1/webhooks/{category}/{provider}`) and S51.2 requires a per-workflow secret URL. Declared in OpenAPI as a public, signature-authenticated route.
3. `POST …/executions` with a repeated `dedupeKey` answers **200 with the original** (`duplicate: true`) instead of 409 (the prompt says both "409" and "returns original"); an idempotent success is the safer reading for at-least-once triggers.
4. `POST /v1/marketplace/purchases` returns 202 while the invoice is unpaid and 200 when paid; the "402" of the table is **not** returned because payment is the buyer's separate `POST /v1/billing/payments` call (needs the buyer's method and return URL).
5. `expiresAt` of a grant is **required** (422 when missing, as the API table says); the "default 90 days" of S54.1 is the UI's pre-filled value.
6. `POST /v1/webhook-endpoints` with `secretRotation` for an existing URL rotates that endpoint's secret (docs/04 has no rotation route).
7. Marketplace quote kind: `marketplace` is already in docs/04 §2.2 (no addition needed).
