# Runbook — onboarding a hosting node (HestiaCP)

Status: the control-plane side is built and tested against a MOCK panel. Steps marked **[LIVE]** have never been run on a real node and need a human with a node and the owner's go-ahead. Nothing here is LIVE-VERIFIED.

Design: [ADR-067](../adr/ADR-067-hestiacp-hosting-panel.md). The platform talks to each node's HestiaCP through its REST API (`POST https://<panel fqdn>:<port>/api/`, `hash=ACCESS_KEY_ID:SECRET`, `cmd`, `arg1..N`) using an **allow-listed set of commands** (`apps/api/src/modules/hosting/internal/hestia/commands.ts`). There is no node agent.

Preconditions: a running compute instance known to compute provisioning (Saudi Arabia: Alibaba ECS via SCCC, Riyadh `me-central-1`; Europe: Contabo `EU`), a fixed panel FQDN pointing at it, and an OS image supported by the chosen Hestia version (Debian 12 or Ubuntu 24.04 LTS are the proposed presets: confirm against the Hestia release notes).

1. **Register** — admin console → Hosting → Servers → Register server (`POST /v1/admin/hosting/nodes {name, computeInstanceId}`, `Idempotency-Key`, `hosting_admin`, MFA step-up). The node starts in `maintenance` with no panel connection.
2. **[LIVE] Install HestiaCP** on the instance with the installer of a pinned, approved version (non-interactive options documented for that version), a fixed hostname, PHP-FPM and MariaDB. Record the panel version.
3. **[LIVE] Node setup script** — `infra/hosting/node-setup.sh` (root, on the node, after Hestia is installed). It is the repeatable form of the next steps and changes nothing that is already right (`--dry-run` shows every command first):

   ```
   # on your workstation: the packages and the access profile come from the platform (nothing in them is secret)
   #   GET /v1/admin/hosting/node-packages  ->  write each packages[].file to <dir>/<packages[].name>.pkg, and accessProfile to <dir>/profile
   sudo ./node-setup.sh --packages-dir <dir>/pkgs --access-profile <dir>/profile \
        --allow-ip <control-plane egress address[,..]> \
        --backup-host-type sftp --backup-host <backup host of THIS node's data region> --backup-user <user> \
        --backup-password-file /root/backup-pass --backup-path /nuzm/<node name> --backup-port 22 \
        --disable-hestia-nightly-backups --key-out /root/nuzm-access-key.txt
   ```

   It does, in this order: **packages** — one Hestia package per plan, `nz-<plan key>` (`v-add-user-package <file> <name> yes`; DISK_QUOTA, BANDWIDTH and DATABASES come from the plan, `SHELL='nologin'`, DNS 0 because DNS is the platform's, no CPU/RAM value because Hestia has none); **access profile and key** — the file `/usr/local/hestia/data/api/nuzm-hosting` is the platform's command allow-list (`commands.ts`, checked for drift by a test) and `v-add-access-key admin nuzm-hosting nuzm-control-plane json` creates the key into a root-only file (never printed); **API** — `v-change-sys-api enable` and one `v-add-sys-api-ip <ip>` per control-plane address (never `allow-all`); **backup host** — `v-add-backup-host <type> <host> <user> <password> <path> <port>` (the password is read from a mode-600 file); **nightly job** — with `--disable-hestia-nightly-backups` the admin cron entries that run `v-backup-users` are removed so the platform's schedule (one backup per site per day, with a row, checksum, quota and region check) is the only one; **`/proc` hidepid=2** — the generated WordPress passwords are WP-CLI arguments for a few seconds and must not be visible to other accounts. Every flag is validated; shell fragments are refused. Packages exist before any site is ordered: an order whose package is missing fails with E_NOTEXIST, never silently on `default`.
4. **[LIVE] Backup host** (the store of THIS node's data region; the Saudi region is Saudi-resident storage, the European one is in the EU). The directory Hestia uploads to must be readable and writable by the control plane's worker as `HOSTING_BACKUP_DIR_<REGION>` (for example `HOSTING_BACKUP_DIR_SA_CENTRAL=/srv/backup/sa-central`, layout `<dir>/<site account>/<archive>`). Hestia documents NO encryption of its archives: protect the directory (disk encryption at rest, access limited to the backup account and the worker) — this is a go-live check, and `HOSTING_BACKUP_SINK_PRODUCTION=yes` is set only after the owner decides D-07. Passwords of SFTP/FTP backup hosts are stored in plain text by Hestia (its own warning): use a dedicated account that can write only its node's directory.
5. **[LIVE] Panel key** — the script left the key in `/root/nuzm-access-key.txt`; type it once into the console (step 6), then `shred -u` the file. Keep one key per node; the key can run `v-run-cli-cmd` (WP-CLI as a site user): keep the API address allow-list tight.
6. **Connect** — admin console → Hosting → Servers → the node → Panel connection: host (FQDN), port (8083), the TLS fingerprint if the panel certificate is self-signed, and the access key (`ACCESS_KEY_ID:SECRET`, write-only; outside production only until the vault decision D-12, otherwise a `vault://` reference).
7. **Test** — "Test connection" runs the inventory: panel version, health, runtimes (PHP versions with a backend template, plus `static`) and capacity (measured by the compute provider, minus the platform reserve). A wrong key is an auth failure; an unreachable panel is an outage; neither is guessed around.
8. **Activate** — "Activate" (`PATCH … {status:'active'}`) needs a panel connection, healthy fresh inventory and reported runtimes. Changing the panel connection returns an active node to maintenance: test it again.
9. **[LIVE] Managed WordPress prerequisites** — each PHP version the node offers needs its CLI binary (`/usr/bin/php<major.minor>`, the one `v-run-cli-cmd` is given); the platform installs WP-CLI per account with `v-add-user-wp-cli` when the first WordPress order arrives (nothing to install globally). Hestia's Quick Install is panel PHP with no CLI/REST entry, so the platform reproduces it from the same documented commands (ADR-068). The install is verified over HTTP against the node (Host header = the site's name), so port 80/443 of the node must answer.
10. **[LIVE] Restore-drill node** — a second, small machine in the SAME data region, registered with `purpose: restore_drill` (`POST /v1/admin/hosting/nodes {name, computeInstanceId, purpose: "restore_drill"}`), set up with this runbook (steps 2–6, its own key), and left in `maintenance` forever (the API refuses to activate it; no order ever lands there). `POST /v1/admin/hosting/restore-drills {backupId, nodeId}` restores a real backup onto it, checks the result, wipes the account and records the duration. Run one drill per plan family after setup and then regularly (monthly proposal). The archive has to reach the drill node's `/backup`: until the staging path is built and confirmed (below) a real node answers `restore: unsupported`.
11. **Monitoring** — `GET /v1/admin/hosting/alerts` (capacity, activation, WordPress, certificates, backups, backup store, panel link, failed drills); the sweep runs on the hosting scheduler or on demand. **The scheduler is OFF by default: set `HOSTING_SCHEDULER_INTERVAL_SECONDS` (> 0) on the API/worker, otherwise no scheduled backup is ever queued, no WordPress row is re-queued and no alert is evaluated** (`POST /v1/admin/hosting/monitor-runs` runs one sweep) (`POST /v1/admin/hosting/monitor-runs`). Thresholds: `HOSTING_ALERT_CAPACITY_WARN_PERCENT` (80), `…CRITICAL_PERCENT` (95), `HOSTING_ALERT_ACTIVATION_STUCK_MINUTES` (20), `HOSTING_ALERT_CERTIFICATE_DAYS` (7), `HOSTING_ALERT_BACKUP_MAX_AGE_HOURS` (36): proposals until the owner sets them.
12. **Day 2** — certificate expiry of the panel itself (a pinned fingerprint must be updated when it changes), key rotation (create a new key, connect it, delete the old with `v-delete-access-key`), version updates (re-run the test), draining and migration (drain-and-migrate runbook).

## Live checks that decide NOT VERIFIED (a human with a node; record each as `LIVE-VERIFIED` with evidence, or leave it NOT VERIFIED)
1. Request format and return codes of the REST API (`POST /api/` form fields; a mutating call with `returncode=yes`); the access-key profile really limits the key.
2. `v-add-user` + `v-add-web-domain` + `v-change-web-domain-backend-tpl` + `v-add-letsencrypt-domain` + `v-list-web-domain-ssl` on a real domain; `v-suspend-user`/`v-unsuspend-user`; `v-delete-user` leaves nothing.
3. Backups: `v-schedule-user-backup` produces `<user>.<date>_<time>.tar`; with a remote backup host Hestia UPLOADS it and (confirm) deletes the local copy; `v-list-user-backups` JSON fields (`SIZE` in MB); the BACKUPS package key; whether `v-restore-user` fetches an archive from the remote host by itself (if yes the staging path below is not needed).
4. **Restore staging** — if Hestia does not fetch it: build `ArchiveStager` (SFTP as a restricted `nuzm-restore` account that can write only the node's `/backup`) — pending; then run a restore drill and read the recorded duration and checks.
5. WordPress: `v-add-user-wp-cli`, `v-run-cli-cmd <user> /usr/bin/php8.x <home>/.wp-cli/wp core download|config create|core install`, the database name Hestia gives (`<account>_wp…`, with the account's hyphen), `v-change-web-domain-tpl … wordpress` (may not exist in every install mode: reported, not fatal), then the site over HTTP: no installer redirect, `wp-login.php` served.
6. Isolation between two accounts on one node (customer isolation on a REAL node): from account A's SFTP/PHP, read and write B's `public_html`, B's database and B's `/home` — all must fail; `SHELL='nologin'`; open_basedir per account.
7. Disk quota (`DISK_QUOTA` is enforced only when Hestia's filesystem quota is on: confirm) and bandwidth accounting.

Rollback: set the node `draining`, migrate sites, `retired` when empty; production data is never dropped by migration down files.
