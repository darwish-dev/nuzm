# SCR-K-10 — Progressive Agentic Coding Engine: model adapter v1.1, read-only tool gateway, agent loop (D-46)

Status: **DECIDED as target architecture by the owner on 2026-11-22 (ADR-066); SPECIFIED here; NOT IMPLEMENTED.** Nothing in this document is a claim about existing behaviour. No code, migration or OpenAPI change accompanies it; each milestone below needs its own implementation slice, report and (where it changes a public contract) owner approval of the exact OpenAPI/database delta.
Governed by ADR-066, ADR-061, ADR-065 (addenda G, H), ADR-015; blockers: D-21, D-42, D-38, HG-09-01, D-18.

## 1. Principles (binding on every milestone)
1. The S-K6 single-call adaptation is preserved as the default and the automatic fallback.
2. Provider-neutral contract; capabilities come from official documentation and probes; unknown = unsupported; no invented API methods.
3. Tool calling is data (a request), never execution. Read-only tools run in an in-memory executor with no OS, filesystem or network access. Programs are run only by a separate Execution Gateway after D-21.
4. Every tool call passes one allow-listed, metered, audited gateway with tenant isolation, limits and explicit permissions.
5. Edits are proposals through the existing safe-change pipeline; AI branch only; mode rules enforced in code.
6. Flags default off; existing APIs, database contracts, flags and controls preserved; changes additive.
7. A capability is `LIVE-VERIFIED` (evidence) or `NOT VERIFIED`. The engine is not called production-ready before its capabilities are implemented and verified (benchmarks, security review, D-42).

## 2. `ModelAdapter` contract v1.1 (additive to 1.0; replaces nothing)
Planned text for `docs/09` §7 (also summarised there as "planned extension"):
- **Version negotiation:** `contractVersion` `1.1.0`; a 1.0 adapter keeps working; the gateway uses v1.1 features only when the model declares the capability.
- **Capabilities (per model):** add `tool-use`, `streaming-tool-calls`, `parallel-tool-calls` to `ModelCapability`; `structured-output` stays.
- **Messages as content blocks:** `ModelMessage.content` stays a string for 1.0 callers; v1.1 adds `blocks: ({type:'text',text} | {type:'tool_call',id,name,args} | {type:'tool_result',callId,content,isError})[]`. The gateway renders the neutral blocks into each provider's format; adapters never expose provider-specific shapes.
- **Request:** `tools?: { name, description, inputSchema }[]` (JSON-Schema subset already used by `@nuzm/domain`), `toolChoice?: 'auto'|'none'|{name}`, `maxToolCalls?`. **Response:** `toolCalls: {id,name,args}[]`, `finishReason` gains `'tool_calls'`.
- **Streaming:** chunks gain `{toolCallDelta}` and `{toolCallDone}`; the gateway assembles and validates arguments before anything is executed.
- **Cancellation:** `AbortSignal` honoured by `complete` and `stream` (exists); a cancelled call reports partial usage.
- **Usage:** `usage` per call including tool-call tokens; `null` stays "not reported" (gateway estimate flagged).
- **Conformance kit** (ADR-011) extended: tool-call round trip, malformed arguments, parallel calls, streaming assembly, cancellation mid-stream, usage reporting, refusal, capability declaration vs probe. The mock gets a scripted tool-calling mode. A provider adapter is registered only when it passes the kit; capabilities it cannot prove are not declared.
- **Providers:** Anthropic (adapter exists for 1.0), OpenAI, Google: each needs its capabilities read from official documentation (cited), data terms attested (HG-09-01), residency decided (D-18) and sandbox/test credentials supplied by the owner (no real credentials generated by the agent). Selection among providers remains an owner decision.

## 3. Tool catalogue — stage 1 (read-only)
All tools act on a virtual, read-only snapshot of ONE project's current files (the run's project) built by the gateway; arguments are validated against the schema; results are bounded and scanned.
| Tool | Input | Output | Limits |
|---|---|---|---|
| `list_files` | `{dir?, glob?, limit≤200}` | `[{path, bytes, origin: template|customer}]` | paths follow the platform path rules; no binary content |
| `read_file` | `{path, startLine?, endLine?}` | text of the range | ≤ 16 000 chars per call; binary and oversize refused with a reason; template-origin files only when the template's `ai_processing` permits (same gate as context assembly), otherwise `not_permitted` |
| `search_code` | `{query (literal), pathGlob?, limit≤50}` | `[{path, line, snippet≤200}]` | literal search over the in-memory snapshot, bounded time and hits; no regex engine exposed |
| `inspect_project` | `{}` | frameworks, dependency names and versions, script NAMES (never run), entry points, tree summary, from the existing detection library | bounded |
Per run: ≤ 60 tool calls, ≤ 400 KB returned in total, ≤ 40 KB per call; a call over any limit returns a structured refusal, never truncated silently. Hostile content in a file (instructions, fences) is data: results are wrapped in the engine's untrusted-content blocks. Outputs are scanned for secrets and canaries before they reach the model.

## 4. Tool Execution Gateway
- **Allow-list per run kind and per mode** (extends `checkToolCall`; an unregistered name is denied and audited, as today). **Permissions:** the run creator needs `ai:write` and read access to the project; the organization needs the flags; a tool never widens what the creator may see.
- **Metering and audit:** every call is recorded in `ai.tool_calls` (redacted arguments, status, duration, `action_hash` where an approval applies) and counted; tokens are metered through the model gateway as today. Budgets, ceilings (calls, bytes, steps, minutes) and the kill switch stop the loop. Tenant isolation: the snapshot is built with the run's `withOrg` context; cross-project and cross-tenant requests are impossible by construction and covered by tests.
- **Separation:** the read-only executors may not import `child_process`, `fs`, `net`, `http` or the sandbox runtimes (enforced by a lint rule and a static test). The reserved execution tools (`run_tests`, `run_build`, `run_lint`, `run_command`) are parameterised TASKS of the Execution Gateway (no free-form command line from the model), not tools of this gateway.

## 5. Agent loop (stage S-AG3)
`PLAN → EXPLORE ⇄ (read tools) → PROPOSE → VALIDATE → APPLY → SUMMARISE`, with `RECOVER` on tool errors, validation errors (≤ 2 repairs, as today) and budget pressure.
- **Plan:** a structured plan stored with the run (what to read, what to change); the customer's plan record (S-K7) supplies requirement and mode.
- **Propose:** the same `{summary, patches[]}` shape as S-K6 (≤ 40 patches), so the apply path is unchanged.
- **Validate (static only until D-21):** schema, workspace consistency, adaptation-mode rules, the shared safety checks, dependency policy, optional parse-only syntax checks through the existing parser sandbox. No test or build is run.
- **Apply:** `ChangeService` on `work/ai`; the diff is part of the run result.
- **Checkpoints and resume:** after every model turn and tool result (`ctx.save`); a resumed run never repeats an applied change; cancellation is cooperative at every step boundary; ceilings: model turns, tool calls, tokens/credits, minutes.
- **Fallback:** a provider without verified tool-use, a disabled flag, or a loop that fails its ceilings falls back to the single-call adaptation (recorded in the run events), never silently to something with more power.

## 10. S-AG1 implementation notes (2026-11-22): decisions taken inside this specification
- **Where it lives:** types, helpers, stream assembler, error normalisation, mock and kit in `packages/adapters/model` (no dependency on the domain package: adapters stay below it); validation of tool-call ARGUMENTS against each tool's schema and the routing extension (`alsoRequires`) in `packages/domain`; negotiation, tool and streaming support in the gateway (`apps/api/.../gateway.service.ts`).
- **Negotiation:** `effectiveCapabilities(contractVersion, declared)`: a 1.0 adapter keeps exactly its 1.0 capabilities (a 1.0 adapter that declares `tool-use` is NOT offered for tools); `streaming-tool-calls` and `parallel-tool-calls` need `tool-use`.
- **Gateway:** `GatewayCall` gains `tools`, `toolChoice`, `maxToolCalls`, `stream`, `onChunk` and message `blocks`; `GatewayResult` gains `toolCalls` (declared tool, arguments satisfy the schema) and `rejectedToolCalls` (with reasons: the caller tells the model, nothing is executed). Tool specs are checked before anything is reserved; the outbound secret scan covers tool results, tool-call arguments and tool specs; a flagged usage estimate counts tool calls as output. An undeclared tool or malformed arguments from a provider fail that candidate (`invalid_response`, not retried on the same candidate).
- **Streaming:** the gateway reads a stream through the assembler and reuses the same reservation, retry, fallback and settlement as `complete`. **A stream that fails after a chunk was delivered is neither retried nor repeated on another candidate** (a caller never receives a delta twice); a failure before the first chunk is retried like any call. Cancellation aborts the stream, releases the reservation and charges nothing.
- **Public contract unchanged:** `GET /v1/ai/models` still lists only the five contract-1.0 capabilities; the OpenAPI delta for the 1.1 ones needs your approval (§7) and is deferred. Routing already uses all of them.
- **Conformance semantics:** the kit runs the 1.0 cases, then the 1.1 cases. A 1.0 adapter must only satisfy the capability-consistency cases and is reported `skipped` for the rest; behaviour cases need a scenario driver (the mock has one; a live provider driver is S-AG4) and are `skipped`, never "passed", without one.
- **Mock:** implements 1.1 (version `1.1.0`) with scripted tool calls; its tool-capable models are opt-in (`MOCK_TOOL_MODELS`), so every existing consumer sees the same two models and the same answers.
- **Not in S-AG1 (dependencies for the next slices):** the tool registry and executors, per-run limits and tool-call audit/metering (S-AG2); the loop (S-AG3); any real provider, probe or live verification (S-AG4); the OpenAPI delta.

## 11. S-AG2 implementation notes (2026-11-22): decisions taken inside this specification
- **Where it lives:** the four tools, the path and glob rules, the read-only workspace and the limits are PURE code in `packages/domain/src/ai/agent-tools/` (no node builtin, no process, no clock, no network: enforced by a lint rule on that directory and by `separation.spec.ts`, which reads the source). The gateway (allow-list, flag, permissions, limits, secret scan, records) is `AgentToolGateway` in the AI module; the project workspace is a provider the app builder registers for the `webapp` run kind (`AgentWorkspaceRegistry`), reusing the S-K6 template rules.
- **The workspace is a snapshot of the RUN's own project** (`ai.runs.project_id`), opened per batch through `ProjectsPort`; the context of a call carries only the run and the step: neither the caller nor the model can name a project.
- **Gates, in order:** `ai.enabled`, `ai.agent.read_tools` (default off, organization row beats global), kill switch; the run exists in this organization, is not finished and is of a kind that may use tools; the run creator's CURRENT permissions (`ai:write` and `builder:read`, active organization); the step belongs to the run; the workspace exists. Per call: allow-list, schema, per-run limits (60 calls, 400 000 result bytes), execution, per-call size limit (40 000 bytes), outbound secret and canary scan of the RESULT, an append-only record.
- **Errors are results:** a refusal inside a batch (bad arguments, unknown tool, a file that may not be read, a limit) is a `tool_result` block with `isError`, a fixed code and a fixed sentence that never quotes an argument, a path, a file or an exception; the gateway throws only for gate failures (flag, kill switch, run, permission, step, project).
- **Sensitive files by NAME** (environment files, keys, credential stores, VCS internals, installed packages) are never listed, read, searched or counted, whether or not such a file exists (no existence oracle).
- **Template permission (rule 5):** an unchanged template file is readable, searchable and summarised only when the template permits AI processing (otherwise path and size only; a withdrawn template counts as not allowed); the customer's own work always is; editing a template file makes it the customer's.
- **Records:** migration `1868__ai__agent_tool_calls` adds `call_id`, `result_bytes` and `error_code` (nullable) and a unique index on (organization, run, call id) to `ai.tool_calls`, so a replayed call is recorded once and the per-run limits are sums over the table. The ownership manifest now lists module `K` as an extender of the `ai` schema (the only way a migration of this module may touch it). Arguments are reduced before storage: a path, numbers, a glob; for a search only the query's length and a 12-character hash.
- **Finding:** my first glob design compiled to a regular expression and a hostile glob (`*a*a*a*a*a*a*a*b`) backtracked catastrophically on a 300-character path. It is replaced by a memoised matcher whose cost is bounded by (path length x token count) whatever the pattern; a test pins it.
- **Execution flag:** `ai.agent.exec_tools` exists as a name only. `AiFlags.execTools()` returns `false` without reading any row; no execution tool exists and the registry has no place to register one.
- **Not in S-AG2:** any HTTP route, OpenAPI change or UI (the tools are an internal service the loop calls); the loop; metering events (a call is counted in `ai.tool_calls`; tokens are metered through the model gateway as before).
